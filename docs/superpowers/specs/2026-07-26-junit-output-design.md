# Экспорт JUnit-отчёта YAxUnit

## Цель

Добавить параметр `--junit-output <path>` в команду `v8-runner test yaxunit`. При его указании команда выгружает оригинальный JUnit XML, сформированный YAxUnit, из временного каталога запуска в путь, заданный пользователем.

Выгруженный файл должен быть побайтово идентичен внутреннему `report.xml` YAxUnit. Нормализация отчёта для текстового и JSON-представления не должна влиять на выгружаемый файл.

## Контракт CLI

Параметр относится к аргументам запуска YAxUnit и поддерживает оба режима:

```text
v8-runner test yaxunit --junit-output build/test-results/yaxunit.xml all
v8-runner test yaxunit --junit-output build/test-results/yaxunit.xml module ОбщийМодульТестов
```

Для Vanessa Automation параметр недоступен.

Абсолютный путь используется без изменения. Относительный путь разрешается от каталога, содержащего основной найденный `v8project.yaml`, даже если в конфигурации указан другой `basePath`.

CLI отклоняет пустой путь и путь без имени файла. Путь, указывающий на существующий каталог, также считается некорректным.

## Границы запроса и компонентов

CLI-параметр добавляется в `TestYaxunitArgs`. На этапе преобразования CLI-запроса путь разрешается относительно основного файла конфигурации и записывается в `TestRequest.junit_output: Option<PathBuf>`. Существующие MCP-запросы передают в это поле `None`, поэтому их поведение не меняется.

Отдельный helper экспорта JUnit отвечает за операции с внешним файлом:

- проверяет и подготавливает целевой путь;
- создаёт отсутствующие родительские каталоги;
- удаляет предыдущий целевой файл до начала build;
- копирует проверенный внутренний отчёт в соседний staging-файл;
- публикует staging-файл через существующий механизм атомарной публикации файлов;
- очищает staging-файлы и метаданные после ошибок.

Координатор тестов управляет последовательностью операций и приоритетом ошибок. Существующий JUnit parser остаётся единственным механизмом проверки корректности XML, а существующая модель отчёта — источником результата тестов и данных для вывода.

## Последовательность выполнения

При отсутствии `junit_output` текущий процесс не меняется.

При наличии параметра команда выполняет следующие действия:

1. Разрешает и проверяет целевой путь до запуска обязательного build.
2. Создаёт отсутствующие родительские каталоги.
3. Удаляет предыдущий целевой файл. Рекурсивное удаление каталогов не выполняется. Ошибка удаления останавливает команду с инфраструктурной ошибкой.
4. Собирает проект и запускает YAxUnit существующим способом с записью внутреннего `<run-dir>/report.xml`.
5. После завершения Enterprise пытается прочитать и проверить внутренний отчёт во всех случаях, когда запуск уже начался, включая ненулевой exit code, таймаут, отмену или ошибку процесса.
6. После успешного разбора побайтово копирует исходный XML в соседний staging-файл и атомарно публикует его в целевой путь.
7. Добавляет шаг выполнения `export_junit` с внешним путём в качестве target и диагностикой о месте сохранения отчёта.
8. Вычисляет существующий результат тестов на основании разобранного отчёта и результата Enterprise.
9. При успешных тестах удаляет временный каталог запуска только после успешной публикации. При упавших тестах сохраняет временные артефакты по существующим правилам.

Параметр `--full` применяется только после разбора XML при выборе компактного или полного текстового/JSON-представления. В экспорте он не участвует.

## Атомарная публикация и устаревший отчёт

Предыдущий целевой файл намеренно удаляется до начала build. Поэтому неуспешный текущий запуск не может оставить отчёт, который выглядит как результат этого запуска.

Новый отчёт записывается в staging-файл с уникальным именем в целевом каталоге. Затем helper использует существующие средства staged publication и замены файла. Размещение staging-файла и целевого файла на одной файловой системе обеспечивает принятую в репозитории кроссплатформенную семантику атомарной публикации и не допускает появления частично записанного целевого файла.

При ошибке записи staging-файла или публикации целевой файл остаётся отсутствующим. Временные staging-файлы и метаданные очищаются по принципу best effort; ошибки очистки включаются в диагностику.

## Ошибки и семантика результата

Инфраструктурными считаются следующие ошибки:

- пустой или некорректный целевой путь либо путь к каталогу;
- невозможность создать родительский каталог;
- невозможность удалить предыдущий целевой файл;
- отсутствие, пустое содержимое, ошибка чтения или некорректный XML внутреннего JUnit после запуска YAxUnit;
- невозможность создать, записать, синхронизировать или опубликовать staging-файл;
- невозможность получить запрошенный внешний артефакт по любой другой причине экспорта.

Ошибки подготовки до запуска YAxUnit, например ошибка build или подготовки конфигурации runner, сохраняют свой существующий приоритет. Предыдущий внешний отчёт к этому моменту уже удалён.

Если Enterprise завершился с ошибкой, но сформировал корректный отчёт, отчёт выгружается до возврата исходного результата: таймаута, отмены, ошибки процесса, ненулевого exit code или падения тестов. Успешный экспорт не меняет этот результат и его exit code.

Если тесты прошли, но экспорт завершился ошибкой, команда возвращает инфраструктурную ошибку. Если одновременно упали тесты и не удался экспорт, статус команды определяется ошибкой экспорта, а сведения о падениях тестов сохраняются в payload и диагностике результата.

Для ошибок экспорта вводится отдельная классификация: они не должны ошибочно обозначаться как ошибки подготовки тестов. Шаг `export_junit` содержит внешний целевой путь и конкретную файловую ошибку.

## Вывод

Успешный экспорт добавляет диагностику следующего вида:

```text
JUnit report exported to <path>
```

Диагностика и шаг `export_junit` присутствуют как при успешных, так и при упавших тестах. Путь становится доступен в текстовом выводе и структурированных деталях выполнения, а вывод команд без нового параметра не меняется.

## Тестирование

Необходимо покрыть следующие сценарии:

- help и разбор CLI для режимов YAxUnit `all` и `module`;
- отсутствие параметра у Vanessa Automation;
- отклонение пустого пути и существующего каталога в качестве target;
- разрешение пути относительно каталога основного файла конфигурации, в том числе при другом значении `basePath`;
- создание отсутствующих родительских каталогов;
- побайтовое равенство внешнего файла внутреннему JUnit fixture;
- идентичность выгруженных данных с параметром `--full` и без него;
- экспорт после падения тестов и ненулевого exit code Enterprise с сохранением существующей семантики exit code;
- экспорт корректного отчёта, сформированного до таймаута, отмены или ошибки процесса;
- удаление старого целевого файла, если новый отчёт отсутствует, пуст, некорректен или не сформирован из-за ошибки подготовки;
- ненулевой exit code при ошибках подготовки target, staging, записи, синхронизации и публикации;
- очистку staging-файлов и метаданных;
- удаление временного каталога успешного запуска после экспорта;
- неизменность существующих тестов и snapshots при отсутствии параметра.

Публичный контракт покрывается интеграционными CLI-тестами. Проверка подготовки пути и ошибок staged publication покрывается узкими кроссплатформенными unit-тестами.
